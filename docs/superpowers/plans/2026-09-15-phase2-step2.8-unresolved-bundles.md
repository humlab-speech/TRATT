# Phase 2 Step 2.8 — Unresolved Bundles Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** On page reload, every LOCAL-mode bundle that was ever created (not just `bundle-1`) is restored from IndexedDB and shown in the bundle list — the ones with no audio resident (which is all of them, since audio is never persisted) show an "awaiting media" state with a per-row re-attach control. Re-attaching compares the picked file's fingerprint against what was originally recorded; a match resolves the bundle into a normal, editable one; a mismatch warns and lets the user override rather than silently binding an annotation to the wrong audio.

**Architecture:** No schema changes — the `bundles` Dexie table (from step 2.6) already has everything needed. This step is new application logic on top of an already-correct schema: (1) a boot-time effect enumerates and restores every bundle's metadata into the NgRx entity collection, reusing step 2.7's `createBundle` action (extended to accept restored content); (2) the bundle list (step 2.7's `BundleListComponent`) grows a per-row "awaiting media" state and re-attach control; (3) a fingerprint (name+size+type+`lastModified`) gates re-attach, extending `SessionFile` to actually round-trip `lastModified` (currently silently dropped — a real gap fixed as a prerequisite here).

**Tech Stack:** Angular 19 (standalone components, signals), NgRx (store/effects/entity), Dexie (existing `bundles` table, no migration).

**Spec:** `docs/superpowers/specs/2026-09-10-workbench-conversion-design.md` — see the "Finding (2026-09-15, during 2.8 planning)" section for the full list of corrected premises and the design this plan argues from.

## Global Constraints

- **No Dexie schema/version changes.** The `bundles` table's `[bundleId+name]` shape already carries everything this step needs. Do not add a `.version(0.7)` or touch `tratt-database.ts`'s version chain.
- **No cryptographic content hashing.** Fingerprint matching is `{name, size, type, lastModified}` against a candidate `File`'s own same fields — cheap, well-precedented, and sufficient given the spec's own words ("warn and let the user override"), not a guarantee. Do not add `crypto.subtle.digest` or any full-file-read hashing.
- **Skip bundles with no persisted `sessionfile`.** `checkAndFillPopulation()` always seeds a default, empty `bundle-1` `options` row for every user, even one who has never dropped a file. A bundle whose persisted `options.sessionfile` is `null`/absent was never actually used — restoring it as "awaiting media" would show a confusing, meaningless row for every first-time user. Only bundles with a real, non-null `sessionfile` are restored/shown.
- **Logs and import-options restoration are explicitly out of scope for this step.** Only `sessionfile` (for the fingerprint + display name) and the serialized `transcript`/`annotation` are restored. A restored bundle's logging history and import-converter state stay at their fresh defaults — restoring those too is a small additive follow-up, not required for "see your bundles and re-attach media to them," and adding it now would grow this already-large step further without serving the "Done when" bar.
- **Legacy pages (`reload-file.component.ts`, `login.component.ts`) are untouched**, same constraint as step 2.7 — nothing in this step changes their behavior; they don't use the bundle-list UI at all.
- **TDD throughout**, per this codebase's Jest conventions.

    * Returns every distinct bundleId present in the `bundles` table. The
    * table's only index is the compound `[bundleId+name]` primary key — no
    * secondary index on bundleId alone — so this is a full-table-scan of
    * primary keys, not an indexed query. Fine at expected row counts (a
    * handful of rows per bundle).

## Final whole-branch review

2. Confirm Task 3's boot-restore effect and the pre-existing `loadOptions$`/`loadAnnotation$` effects (still hardcoded to `DEFAULT_BUNDLE_ID`) don't double-restore or conflict for `bundle-1`.
3. Confirm Task 5's editor-mount wiring (whatever it turned out to be, per that task's own investigation) actually works for a freshly-resolved bundle, not just in that task's own isolated unit tests — this is exactly the class of cross-task integration bug step 2.7's final review found (a fix that satisfies its own task's tests but doesn't actually close the loop end-to-end).
