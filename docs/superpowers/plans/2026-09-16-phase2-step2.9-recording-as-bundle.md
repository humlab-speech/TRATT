# Phase 2 Step 2.9 — Recording as a Bundle Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A user can record audio from the microphone directly in the `/workbench` UI and have it become a bundle through the exact same multi-bundle machinery a dropped file already uses — including an interrupted-recording recovery banner, reachable from the workbench, that wasn't reachable from there before.

**Architecture:** This step turns out much smaller than the original conversion plan's one-line "second ingest path... through the same BundleService" description implied. There is no `BundleService` anywhere in this codebase (confirmed false at every prior step of this conversion effort too) — the real multi-bundle machinery is `TrattDropzoneService`'s decode pipeline (step 2.7) feeding `WorkbenchComponent.startSession()`'s per-entry bundle-id loop. `TrattDropzoneComponent` already has a `public addFile(file: File): void` method with the doc comment *"Stage a programmatically supplied file (e.g. from the recording panel)"* — written for exactly this integration, unused until now. The recording panel (`RecordingPanelComponent`) already hands its finished recording up as a plain `File` via a `(useRecording)` output, and the legacy `login.component.ts` already wires that straight into `dropzone.addFile(file)` for the old single-bundle flow. This step is mostly: mount the recording panel in the workbench, wire the same handoff, and get the multi-bundle path — already built in 2.1-2.8 — for free.

**Tech Stack:** Angular 19 (standalone components, signals), NgRx (unchanged by this step), existing `RecordingService`/`RecordingPersistenceService` (a separate Dexie database, `tratt-recordings`, untouched by this step — no changes to recording capture/persistence itself).

**Spec:** `docs/superpowers/specs/2026-09-10-workbench-conversion-design.md` — see the step-2.8 finding's point 4 ("The 'recovery banner' referenced by step 2.9's own plan text is unrelated and not reusable... no file-picker/re-attach UX exists anywhere in this codebase to model step 2.8's UI on") for background on why 2.8 couldn't reuse this banner; this step is where it actually gets connected to the bundle system instead.

## Global Constraints

- **Do not touch `RecordingService`, `RecordingPersistenceService`, `tratt-recording-database.ts`, or the `tratt-recordings` Dexie database.** Recording capture, chunked persistence, and crash-recovery listing already work correctly and are out of scope — this step only connects their existing output (`RecordingPanelComponent`'s `useRecording` File-emit) to the bundle system, the same way `login.component.ts` already does for the legacy flow.
- **Do not touch `login.component.ts`/`.html` or `reload-file.component.ts`/`.html`.** Matching every prior step's constraint in this conversion effort — the legacy `/local` flow stays exactly as it is.
- **Recording is a pre-session ingest path, same limitation the dropzone itself already has.** Step 2.7's plan explicitly deferred "drop more files into an already-active session" as out of scope (`startSession()` remains a single-shot gesture). A recording made mid-session (after `startSession()` has already run) stages into the dropzone the same way a dropped file would in that state — reachable on the next full session start, not immediately turned into a live bundle. Do not build a "mid-session ingest" mechanism in this step; that is a separable piece of future work this step does not need to unblock.
- **No new test coverage is required for `RecordingService`/`RecordingPersistenceService`/`RecordingPanelComponent`'s own internals** (their existing behavior — recording capture, chunk persistence, session recovery listing — is unchanged and already has some coverage per the exploration for this plan). This step's own tests cover only the NEW integration surface: the workbench mount, the `useRecording` handoff, and any navigation-guard changes.
- **TDD throughout**, per this codebase's Jest conventions.

### Task 1: mount the recording panel in the workbench and wire the bundle handoff

**Interfaces:**
- Consumes: `TrattDropzoneComponent.addFile(file: File): void` (existing, unused until now),
  `RecordingPanelComponent`'s `(useRecording)` output (existing), `RecordedFileService.recordedFile`
  setter (existing, already injected into `WorkbenchComponent`).
- Produces: nothing consumed by a later task — this is the core integration.

**Steps:**

1. Read `RecordingPanelComponent` (`apps/tratt/src/app/core/component/recording-panel/recording-panel.component.ts` and `.html`) in full, and `login.component.html`'s mount of it (around line 245-257, the local-mode "record" tab) for the exact selector/inputs/outputs this component expects. Also open `docs/superpowers/specs/reference/TRATT Workbench.dc.html` (the interactive mockup referenced throughout this conversion effort's design doc) and check whether it shows a recording affordance in the workbench's left rail — if it does, match that intended layout; if the mockup doesn't cover this (Phase 2 work postdates the original mockup), use your own judgment for a reasonable placement and say so in your report, don't block on it.
2. Decide, and document in your report, how the recording panel is surfaced alongside the existing `<tratt-dropzone>` in the workbench's left rail — a tab/toggle between "Drop files" and "Record" (matching `login.component.html`'s own existing tab pattern for the local-mode nav, the closest precedent in this codebase) is a reasonable default if the mockup doesn't dictate otherwise. Whatever you choose, both the dropzone's pending-file list (with the "Start" button) and the recording panel (with its recovery banner) must remain reachable — don't make one permanently replace the other.
3. Import `RecordingPanelComponent` into `WorkbenchComponent`'s standalone `imports` array. Mount `<tratt-recording-panel (useRecording)="onUseRecording($event)">` in the template, in the area decided above. `RecordingRecoveryBannerComponent` needs no separate mounting — it's already nested inside `RecordingPanelComponent`'s own template (`recording-panel.component.html:1-7`) and will render automatically once the panel itself is mounted and its `ngOnInit()` calls `refreshRecoverable()`.
4. Add to `WorkbenchComponent`:
   ```ts
   onUseRecording(file: File): void {
     this.recordedFileService.recordedFile = file;
     this.dropzone?.addFile(file);
   }
   ```
   This mirrors `login.component.ts:109-113`'s existing `onUseRecording` handler exactly (`recordedFileService.recordedFile = file; this.dropzone?.addFile(file);`) — the one difference is `login.component.ts` also does `this.activeTab = 'upload'` afterward (switching its own local tab state to show the newly-staged file in the upload/file list view); if Task 1's step 2 introduced an analogous tab/toggle state in `WorkbenchComponent`, switch it the same way here so the user immediately sees the recorded file land in the dropzone's pending list. If no tab state was introduced (both views always visible), this step is a no-op — just don't silently drop the equivalent UX if you did add tabs.
5. Read `WorkbenchComponent`'s `@ViewChild(TrattDropzoneComponent) dropzone?: TrattDropzoneComponent;` declaration (existing) — confirm it's still valid for this new call site (i.e. the dropzone remains in the DOM/reachable via ViewChild regardless of whether a tab/toggle is currently showing the recording panel instead — a `@ViewChild` on a component that's conditionally rendered via `@if` becomes `undefined` when hidden; if you introduce an `@if`-gated tab structure in step 2, verify the dropzone stays queryable — e.g. by NOT `@if`-gating the dropzone itself, only visually toggling which panel is emphasized, or by using `{static: false}`/checking `ngAfterViewChecked` timing. Report exactly how you handled this — it's a real pitfall, not a formality.

**Tests** (write first, confirm red, then implement): mock `dropzone` and `recordedFileService` per this spec file's existing conventions (already established for `startSession()`'s tests). Dispatching `onUseRecording(file)` sets `recordedFileService.recordedFile === file` and calls `dropzone.addFile(file)` with that exact file. A second test confirms the recording panel is actually present in the rendered template (a `fixture.debugElement.query` for the `tratt-recording-panel` selector, or equivalent, matching how this spec file already asserts on `tratt-bundle-list`'s presence from step 2.8's Task 6).

### Task 2: unsaved-recording navigation guard for `/workbench`

**Files:**
- Read first, modify only if the investigation in step 1 below finds a real gap: `apps/tratt/src/app/app.routes.ts`, `apps/tratt/src/app/core/pages/login/login.deactivateguard.ts`, `apps/tratt/src/app/core/pages/workbench/workbench.component.ts`

**Steps:**

1. **Investigate before changing anything.** `WorkbenchComponent` already calls
   `this.recordedFileService.checkUnsaved(this.modService)` inside `abortTranscription()` (an in-app
   "quit/abort" action) — so an in-app path is already guarded. What's NOT yet confirmed: does
   `login.component.ts`'s `ComponentCanDeactivate`/`login.deactivateguard.ts` pattern actually wire
   through Angular Router's `canDeactivate` for the `login` route today (grep `app.routes.ts` for
   `canDeactivate`/`CanDeactivate` — a first pass during planning found zero hits, meaning this guard
   may not actually be active via routing at all, only reachable through the explicit in-app action
   path, same as `WorkbenchComponent`'s current `abortTranscription()` call). Trace this fully: read
   `login.deactivateguard.ts`, find every place `ComponentCanDeactivate`/the guard function is actually
   referenced (route config, a functional guard, or nowhere), and report precisely what you find.
2. If the investigation finds the legacy `/local` route genuinely has router-level `canDeactivate`
   protection that `/workbench` lacks (i.e. navigating away — closing the tab aside, which no
   client-side guard can catch anyway — via an in-app link/programmatic navigation — would silently
   lose a staged, unsaved recording on `/workbench` today with no guard at all, whereas `/local` would
   prompt), add the equivalent for the `workbench` route in `app.routes.ts`, matching whatever
   mechanism `login`'s route actually uses (functional guard or `ComponentCanDeactivate` class,
   whichever the investigation reveals is the real, active pattern — not a guess).
3. If the investigation finds `/workbench` is already adequately covered (e.g. because leaving
   `/workbench` today always goes through the in-app `abortTranscription()`/logout path already
   guarded, and there is no OTHER unguarded route-level navigation away from an active LOCAL session
   reachable from the workbench), make no change — report this finding clearly instead, with the exact
   reasoning, so it's not mistaken for a skipped task.

**Test** (only if a change is made in step 2): a test asserting the route guard is registered and
returns `false`/prompts when a recording is staged unsaved, `true` otherwise — matching whatever
existing test pattern (if any) covers `login`'s route guard, or a new equivalent if none exists.

## Final whole-branch review

schema — it wires an existing, working `File`-emit into an existing, working multi-bundle pipeline).

   plausible against the actual routing code, not just trusted from the task's own report.
