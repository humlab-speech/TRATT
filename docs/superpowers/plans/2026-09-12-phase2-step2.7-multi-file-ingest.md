# Phase 2 Step 2.7 — Multi-File Ingest Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Dropping several audio files onto the workbench dropzone and clicking Start produces several independently selectable, independently editable, independently undo-scoped bundles, each of which persists its own IndexedDB row and survives a bundle-eviction/re-selection cycle — without changing behaviour for the legacy `/local` pages (`reload-file.component.ts`, `login.component.ts`), which keep using exactly one bundle (`bundle-1`) as they do today.

**Architecture:** Every piece of multi-bundle *infrastructure* (real generated bundle ids, an `[bundleId+name]`-keyed IDB table, a `Map<bundleId, AudioManager>` registry with LRU eviction keyed off a store-driven `selectedBundleId` signal, a per-bundle-pure undo/redo reducer) already landed in steps 2.1–2.6. Nothing in the UI has ever made `selectedBundleId` vary, and the ingest path (`TrattDropzoneService` → `WorkbenchComponent.startSession()` → `onLoginLocal$` effect → `login-mode.reducer.ts`) collapses every dropped file down to one bundle. This step wires the existing infrastructure up to real multi-file drop-and-select UX: it does **not** invent new persistence or eviction mechanisms, it makes the ones already built reachable and correct for N > 1 bundles.

**Tech Stack:** Angular 19 (standalone components, signals), NgRx (store/effects/entity), RxJS, Dexie (via `TrattDatabase`/`IDBService`, unchanged schema — step 2.6 already gave `bundles` the right shape).

**Spec:** `docs/superpowers/specs/2026-09-10-workbench-conversion-design.md` — see in particular the step-2.5 outcome paragraph ("step 2.7 must land re-decode-on-reselection and actual envelope consumption together with whatever UI first makes bundle re-selection reachable") and the step-2.2/2.3 notes ("`selectSelectedBundleId` is hard-wired... revisit once step 2.7 makes `selectedBundleId` genuinely variable").

## Global Constraints

- **Legacy callers of `loginLocal` must see zero behaviour change.** `reload-file.component.ts` and `login.component.ts` (the old, untouched `/local`-era pages) call `AuthenticationStoreService.loginLocal(files, annotation, removeData)` today with no bundle-id argument. Every change to `loginLocal`'s signature/action payload/effect must be strictly additive (a new optional parameter/field) and must produce byte-for-byte the same bundle id (`DEFAULT_BUNDLE_ID`, `'bundle-1'`) for these callers that it produces today. Do not touch `reload-file.component.ts` or `login.component.ts`.
- **Bundle ids are generated where the matching `AudioManager` is registered, never independently in two places.** `AudioService.registerAudioManager(bundleId, manager)` and the bundle entity that ends up in `EntityState` must always agree on the exact same id for the exact same audio. Generate the id once, in `WorkbenchComponent.startSession()` (Task 5), and thread it through — never let the effect independently call `generateBundleId()` for a file the component already registered a manager for.
- **The existing single-bundle `loginLocal.prepare` → IDB-save race → `loginLocal.success` gating in `onLoginLocal$` is untouched for the first/only bundle.** This is real, tested, load-bearing session-start logic (modal-confirm-before-delete, wait-for-persisted-options-before-flipping-`sessionReady`). Multi-bundle support is added *alongside* it (dispatch `createBundle.do` for bundles 2..N), never by restructuring it.
- **`load*` IDB effects that only ever fire at app boot (`loadOptions$`, `afterOptionsSuccess$`/loadLogs, `loadAnnotation$`, `loadImportOptions$` — the ones with a literal `DEFAULT_BUNDLE_ID` argument, not a `mode === LOCAL ? DEFAULT_BUNDLE_ID : undefined` ternary) are explicitly out of scope for this step.** Restoring more than bundle-1 from a page reload is step 2.8's concern ("post-reload rows awaiting media, with per-row re-attach") — these call sites are correct as they stand until 2.8 lands. Only the **save**-side call sites (the ones using the ternary pattern) are in scope here.
- **Transcript-file-to-audio-file pairing stays single-bundle for this step, documented as a deferred gap, not silently dropped.** `TrattDropzoneService`'s `_oaudiofile`/`_oannotation` singular fields (used only for matching an imported transcript file to "the" audio for annotation import) keep their current behavior — they always pair with the most recently decoded audio file. Multi-file *audio* bundles are fully supported; multi-file audio-plus-matching-transcript-import pairs are not generalized in this step. Record this explicitly in the spec (Task 1).
- **TDD throughout.** Every task writes a failing test first, confirms red, then implements to green, per this codebase's Jest conventions (`@jest/globals` imports, `jest-preset-angular`).
- **"Edits survive reload" (the original conversion plan's Phase 2 "Done when" criterion) lands only half here.** This step makes every bundle's edits persist to its own correct IndexedDB row the moment they happen (Task 3), so nothing is lost *while the tab stays open*. Actually restoring more than bundle-1 *after* an actual page reload requires the per-row re-attach UX that is step 2.8's explicit scope ("post-reload rows awaiting media") — until 2.8 lands, reloading the page still only brings back bundle-1. This is a deliberate scope boundary, not an oversight; see the load-side Global Constraint above.
- **`nx lint tratt` has 3 pre-existing, unrelated failures** (`tratt-database.ts:374`, two in `transcr-window.component.html:74`) — not this project's responsibility; don't "fix" them as drive-by work, and don't let a diff-scoped lint check on files you didn't touch block a task.

2. `readAudioFile()` (line 257) has the "destroy previous audio manager" branch (lines 289-296):

3. Add the new getter:

     return this._files

6. `remove(id: number)` (line 177) and `stopFileProcessing()` (line 347): `stopFileProcessing` currently does `this._audioManager?.stopDecoding()` (line 356) — the singular field. 7. **Sequential decode queue.** Today, `add()` calls `this.readFile(progressFile).subscribe(...)` (line 155) directly and immediately for every dropped file — with `afterDrop()` in `tratt-dropzone.component.ts` looping `for (const file of files) { this.trattDropzoneService.add(file); }` without awaiting, multiple files' decode chains (`readFile` → `forkJoin` → `exhaustMap` → `decodeArrayBuffer`) start concurrently and race. Change `add()` to push `progressFile` onto `this._decodeQueue` (`this._decodeQueue.next(progressFile)`) instead of calling `this.readFile(progressFile).subscribe(...)` directly — keep the existing `error` handling (the same `error: (error) => {...}` callback) by handling errors *inside* the piped observable (e.g. `catchError` per-item so one file's decode failure doesn't kill the queue for subsequent files) rather than on the outer subscription. `concatMap` guarantees the next file's `readFile`/decode doesn't start until the previous one's observable completes — verify this with a test (see below).
